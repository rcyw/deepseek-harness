# Agent Note: 显式唤醒 Agent 的待处理 inbox 工作

Status: implemented

[English](2026-08-30-explicit-agent-wake.md) | 中文

## 问题

持久 inbox 输入可能在进程丢失后继续存在，并在恢复 Session 时重新出现。`resume()` 会重建该输入，但刻意不启动模型轮次。否则，恢复 owner 只能插入第二条唤醒消息，这会改变 canonical 审计日志，并可能重复已经持久化的任务意图。

## 决策

公开 `Agent` 接口要求实现 `wake(): void`。它请求驱动 inbox 中已经存在的输入，绝不插入、移除或重写消息。inbox 为空时，该调用不执行任何操作。

当存在待处理输入时，空闲 agent 同步启动驱动器。实时驱动器已经拥有待处理工作。maintenance 或活动取消操作之后的唤醒会锁存到该活动收敛，但 disposal 不会为之后的工作做准备。调用方使用 `whenIdle()` 观察由此产生的整个 agent 活动，而不会把 `wake()` 当成单条消息的结果。

`resume()` 在重建持久 inbox 后仍保持静止。恢复 owner 检查持久证据，只在执行该确切待处理输入安全时调用 `wake()`。

## 考虑过的替代方案

**自动驱动每个恢复后的 inbox。** Resume 也用于检查或继续那些注入上下文刻意等待后续输入的 Session。自动执行会让持久化加载成为外部副作用边界，并移除恢复 owner 的决策点。

**插入合成 follow-up 或重新插入持久消息。** 两种选择都会增加一条持久意图记录，并可能重复任务交付。唤醒操作必须保留已有消息身份与审计历史。

**暴露具体循环辅助函数。** 消费方将依赖 `dsh-agent-loop` 内部实现，并让公开 `Agent` 实现不可替换。该操作属于每种驱动器都要实现的接口。

## 结果

进程恢复消费方可以恢复并执行一条 canonical 待处理消息，而无需制造输入。空 inbox 或只检查的 resume 仍保持静止。每个 `Agent` 实现与精确测试桩都实现这个必需方法，而仅调用它不会增加 Session 事件或模型可见文本。
